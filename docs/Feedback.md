## 2026-10-14
- **Add location confirmation:** For a new location, show that it will be created and list its details. Avoid `Unknown -> ...` and existing-value changes, which make the flow look like an edit. Clarify the impact, for example: “This adds a location; existing plans won’t change.”
- **Add product fields:** Clarify that “Pack” describes the package (for example, “20 bars per box”) and “Counted in” is the unit used for stock quantities (“box” or “bar”). A number like `20` alone is ambiguous.
- **Product form wording:** Rename “Pack” and “Counted in” to clearer labels, and show helper text with an example beneath each field. Feedback only for now; do not change the app yet.
- **Inventory UI feedback:** The product dropdown and location cards make the relationship hard to scan. Avoid a full product-by-location grid and a tree; both make it harder to navigate at scale.
- **Inventory scale constraint:** The inventory view must remain usable with around 100 products and 100 locations; a full product-by-location matrix would expose 10,000 cells and be difficult to scan.
- **Agreed inventory layout:** Add a two-way toggle, **By product** / **By warehouse**. In product mode, search products and see stock across warehouses; in warehouse mode, search warehouses and see products at that location. Keep each view searchable and paginated so the UI never shows all 10,000 possible records at once. Approved 2026-10-14.
- **Add order review:** The confirmation step omits Product and Ships from (they keep their preselected defaults, so they aren't shown as changes). For a new order, show every field so the user can verify what they're saving. Same on Add incoming shipment: Product and Arriving at are missing from the review.
- **Order priority wording:** The field is "Priority" and one option is also "Priority" (the other is "Standard"), which reads as "Priority: Priority". Consider options like "High priority" / "Standard".
- **Receiving limit is unclear:** Users read it as storage capacity ("Wakanda already has stock, will it overflow?"). It is actually an unloading limit per day, and the planner only uses it to cap emergency transfers (shared/planner/plan.ts). It does not check supplier shipments, other arrivals on the same day, or existing stock. It is also one number shared by every product, shown as "200 bags/day" for Vibranium and "200 units/day" for Gun, and never added up across products (200 bags + 200 units on the same day both pass). Clarify the label (e.g. "Most it can unload per day") and decide whether storage capacity is needed.
- **Proposal (not decided): per-item limit per warehouse.** Example: "Wakanda can hold at most 500 bags of Vibranium". Suggested placement is an optional field on the stock record (product x warehouse), not the Add product form, which doesn't know the warehouses and would need 100 fields for 100 warehouses. Leaving it blank means no limit. Alternative: a product-level default with per-warehouse overrides. Open question: is this a storage limit (how much fits) or a receiving limit (how much can be unloaded per day)?
  - User direction (2026-10-14): storage matters, likely both. Storage = new, optional, per product x warehouse; warn when stock + incoming exceeds it. Unloading = keep the existing per-warehouse limit and fix its label. Build storage first if only one.
- **Supplier arrival should be a lead time, not a fixed date:** The backup supplier's "Arrival" is a fixed date entered at setup. The planner already uses it correctly (rejects the supplier as "too late" if it can't arrive before the affected orders are due; asks for it if blank, shared/planner/plan.ts). But a backup supplier's delivery time really depends on when you place the order, so a fixed date goes stale. Proposal: ask "Can deliver within ___ days/hours" and compute arrival from the time of the delay.
  - User point (2026-10-14): at setup we don't know if we'll ever order from the backup supplier, so its stock, price and arrival are guesses that go stale. The real question ("can you deliver 45 bags to Wakanda by 20 Oct 10 AM?") only exists once a delay happens. Proposed flow (not decided): setup records only who / what / where, plus an optional typical lead time as a rough guide. When a delay happens, the supplier option shows "Ask supplier" with a drafted message containing the exact quantity and deadline. The option stays "waiting for supplier" until the user records the reply (typed in, or attached and read by Gemini). Only a confirmed reply makes it ready.
